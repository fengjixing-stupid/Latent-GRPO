# Latent-GRPO Requirements Traceability Matrix

> 阶段：Phase A（只读审计与实现设计）  
> 规范优先级：target variables > validation > storage > system > orchestration > master prompt  
> 字段身份：`(storage_table, field_name)`；同名字段跨表重复是规范要求，不得合并。  
> 当前状态仅使用 `planned` 与 `blocked`；本阶段不声称任何训练字段已经 implemented/verified。

## 覆盖摘要

- 规范字段记录数：420
- 唯一字面字段名：330
- 目标：严格覆盖 `spec/target_variables.md` 的逐表逐字段清单，并显式标注不可得项、理由、测试与证据路径。
- 完整性判定以表限定字段记录为准，而不是仅以唯一字面名称计数。

## 负向要求追踪

| requirement_id | 禁止项 | 计划验证 | 当前状态 |
|---|---|---|---|
| NEG-001 | 不允许自定义 `position_ids` 进入训练主逻辑 | AST/源码扫描 + smoke 事件检查 | planned |
| NEG-002 | 禁止以 reorder/filter/select 后的局部 batch index 冒充稳定 `trajectory_id`；稳定 ID 必须在 repeat 后、任何 reorder/filter/select 前创建并随记录持久传播 | stable-ID 单元测试 + reorder/filter/select 回归 + schema/Parquet 主键检查 | planned |

| NEG-004 | 不允许创建图像、可视化或图像路径字段 | schema/产物树/文本扫描 | planned |

### 9.1 覆盖检查方法

1. 按 target_variables 的公共字段、Stage 1 train/eval、Stage 2 diagnostic/mixture/mask/signal/group、Stage 3 definition/metrics/benchmark、Stage 4 definition/metrics/benchmark、run_config、memory-only intermediates 分区建立 canonical manifest；不从任意 Markdown code block 盲抽，因为禁止项和示例会造成假目标。
2. 下一阶段 validator 从 Arrow/JSON schema manifest 读取实际 `(storage_table, field_name)`，与 canonical manifest 作集合差得到 `missing_fields`，另检查禁止字段交集、credit/diagnostic 默认 availability、memory-only 不落盘。验收为 `missing_fields == []`。
3. 模板行 `<family>_*` 与 `<metric_name>__*` 在 schema 生成时展开为实际 family/metric 名；模板本身不写入 Parquet。
